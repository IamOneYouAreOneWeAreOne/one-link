## 1. Executive summary

One Link ships a serious peer-to-peer chat, file transfer, and call platform. The underlying primitives (Noise sessions, Double Ratchet, ML-DSA hybrid signatures, Sphinx onion routing, threshold recovery, attestation, native Rust hot paths) put it ahead of nearly every messenger in the privacy axis. The UI is more polished than most P2P apps. But it is **not yet at parity with consumer chat apps on the surfaces that drive daily-use feel**.

The audit identifies gaps in seven categories, ordered by user-impact:

1. **Acute reliability gaps** that surface as silent failures (send hangs forever, chat doesn't live-render on receiver, calls don't propagate to the second computer). Many were fixed in the May 17 batch. The rest are about getting the rebuilt exe into the field and making peer-version mismatches visible.
2. **First-run experience.** No welcome wizard, no permission preflight, no tutorial. A new user opens One Link to a blank chat pane and a single "Pair a device" button. They learn by trial.
3. **Composer parity.** No emoji picker. No GIF/sticker support. No mentions. No `/me`. No schedule send. No voicemail / async-voice surface even though the doctrine names it.
4. **Photo and file experience.** Now clickable as of today. Still missing image gallery swipe, image markup before send, camera capture, file rename before send, EXIF stripping, video player polish.
5. **Call experience.** Audible ringback and ringtone are missing. Missed calls don't appear in chat. Reconnect on network drop ends the call. No screen share, PIP, or background blur. No call history view.
6. **Trust visibility.** Capabilities, SAS state, and verification level exist in the data model but are not consistently visible. Users can't easily tell "is this peer fully verified or just blindly trusted".
7. **Polish.** No sound effects. No haptic feedback. No system tray badge. No "what's new" modal. No in-app bug report. Microcopy is mostly excellent but inconsistent in tone across surfaces.

The recommended approach is to ship **Phase 1 (current-build feels finished) before anything else**, because the value of every later phase compounds on having a non-flaky baseline. Phases 2 through 7 are sequenced by user-impact / cost ratio. None of these are speculative — every item has a concrete implementation sketch in Appendix E.

This audit deliberately does not include calendar timelines. Acceptance gates ship work; calendar dates don't.

## 2. Methodology and frame of reference

### Source of truth

This audit reads the shipped code, not the design docs. When a doctrine doc and the running code disagree, the running code wins (the user never sees the doctrine). All findings include file path and line references that can be verified independently.

### Frame of reference

Comparison apps and what they're notable for:

| App | Notable for |
|---|---|
| Signal | Privacy-first defaults, sealed sender, safety numbers, disappearing messages |
| iMessage | Polish, Tapback reactions, message effects, SharePlay, Apple ecosystem continuity |
| WhatsApp | Mass-market simplicity, view-once media, last-seen privacy, voice messages |
| Telegram | Sticker / GIF marketplace, channels, polls, themes, custom emojis, schedule send |
| Discord | Voice channels, screen share + audio, slash commands, custom emojis, threads |
| AirDrop | One-step file transfer, auto-discover nearby, multi-file drop, cross-Apple |
| Quick Share | AirDrop equivalent across Android + Windows, drag-drop simplicity |

Each section identifies what the comparison apps do, what One Link does today, what the gap is, and what the concrete fix looks like.

### What "exhaustive" means here

A real audit names every surface, not just the headline ones. This document is long on purpose: each surface includes the buttons, modals, toggles, edge cases, error paths, and empty states associated with it. Sections that look short have shorter shipped surface to cover.

### What this audit does not cover

* Backend architecture, cryptography choices, or threat model. Those are covered in `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, and the per-phase plan docs.
* Build systems, CI, release engineering.
* The Coherence Language platform underneath. That's a separate audit subject.
* Marketing copy or website copy. The `One_link_Website` project is tracked separately.

## 3. Right-now pain that needs to clear before anything else

These are not feature requests. They are blockers: the things a user just hit and that make every other future improvement irrelevant until they're resolved.

### 3.1. The bundled exe is the OLD code

The daemon listening on this machine right now is `$HOME\Projects\Coherence\One_link\dist\one-link\one-link.exe` (a PyInstaller bundle). The source tree contains the May 17 batch (`_broadcast_tail` regression fix, bulletproof send, collapsible long messages, click-to-open files, queued-with-real-reason, Retry-now button). **None of these reach the user until the exe is rebuilt.**

**Fix:**

```powershell
# From repo root
$env:PYTHONIOENCODING="utf-8"
python scripts/build_binary.py --gui
```

Then copy the contents of `dist/one-link/` to Computer 2.

### 3.2. The peer card says "Verified · on Wi-Fi · 69 ms" but messages queue

The presence indicator (mDNS-level) is decoupled from the wire-path health (Noise channel state). Today the UI exposes only the presence indicator. Users see "online" and don't understand why their messages queue.

**Partial fix (shipped May 17):** queued bubbles now surface the daemon's actual reason ("Could not establish a secure connection with the other device.") and a `Retry now` link.

**Remaining fix:** the peer card should *also* expose the wire-path health. Concrete proposal:

* Small colored dot inside the peer's avatar circle: green (channel active), yellow (channel idle but reachable), red (channel can't establish or peer is older).
* On hover, a tooltip: "Channel established 4m ago · Last bytes 12s ago · Same version as you".
* The current ✓ Verified pill stays, but it's distinct from the channel-health dot.

### 3.3. Peer version mismatch is invisible

Two daemons on different builds will sometimes work, sometimes fail. The user has no way to know which build the other side is on.

**Fix:**

* Every wire handshake exchanges `daemon_version` and `wire_capability_set` ([`src/one_link/capabilities.py`](src/one_link/capabilities.py) already has the capability registry; add `daemon_build` as a top-level field on the handshake).
* The peer card row shows "On v0.21.x · matches you" (gray) or "On v0.20.6 · older than you (your build is v0.21.x)" (yellow).
* When peer is older, expose an "Update this device" affordance that sends them the bundled exe over the file channel.

### 3.4. Send button briefly returned "Queued · Will send when the path is healthy" with no reason

**Partial fix (shipped May 17):** the bubble now surfaces the daemon's translated user-facing copy.

**Remaining fix:** when the daemon's reason is `handshake_failed` AND the peer's version is older, the bubble should say so explicitly: "Queued · The other device is on an older build. Click *Update them* in the peer card."

### 3.5. Computer 2 doesn't render incoming calls

Confirmed root cause: Computer 2 is on the OLD bundled exe, which has the pre-`_broadcast_tail`-wrap fix. After Computer 2 is updated, this clears. Add a section to the diagnostics overlay that confirms peer-side WS event delivery (already partially built into `live_ws_monitor.py` — surface it as a UI option).

### 3.6. Long pasted messages don't visibly send

**Fixed May 17.** Optimistic bubble + 25s client timeout + 20s server `wait_for` + retry chain.

### 3.7. Files in the chat aren't clickable

**Fixed May 17.** Click-to-open with lightbox for images, new-tab for non-images, sender-side File cache so outbound bubbles also open, hover lift, keyboard-accessible.

### 3.8. Acceptance gates for Phase 1

Before any new feature work:

| Gate | Pass criterion |
|---|---|
| Rebuild | `dist/one-link/one-link.exe` is the May 17 source build |
| Peer version surface | Peer card shows "matches you / older / newer" |
| Channel-health dot | Distinct from presence dot, accurate within 30s |
| Send + receive | Round-trip TEXT to Computer 2 lands live, no refresh |
| Call originate | Call from Computer 2 raises ring overlay on Computer 1 within 2s |
| Call accept | Both sides flip to active surface within 1s of accept |
| Photo round-trip | Sender clicks own outbound thumbnail and opens lightbox |
| Photo round-trip 2 | Receiver clicks inbound thumbnail and opens lightbox |
| Long-message collapse | >600-char message renders with Show more, click to expand |
| Queued reason | Queued bubble shows daemon's user-facing reason text |
| Retry now | Queued bubble's Retry now link fires a fresh send |

When all of these pass on both machines, Phase 1 is done.

## 4. First-run and onboarding

### 4.1. Current state

**[Corrected]** One Link ships a real first-run experience, not a placeholder.

* **6-step welcome wizard** (`#onboarding-backdrop`) at [`index.html:7486-7592`](../src/one_link/web/index.html#L7486):
  * **Step 1 — You are One.** Welcome screen with glyph, tagline, proof chips ("No account", "Encrypted", "Works nearby"), Set up / Skip.
  * **Step 2 — Name this device.** Text input with placeholder ("Alex's laptop"), shows device card preview.
  * **Step 3 — Create your One identity.** Identity creation with "I already have one" branch to step 4.
  * **Step 4 — Add your phone or laptop.** QR rendering, copy-code, SAS confirmation ("Codes match" / "Codes do not match"), Pair later branch.
  * **Step 5 — Send something to yourself.** First-action prompt with Send test message / Send a file / Do this later.
  * **Step 6 — One Link is ready.** Completion checklist, Review safety button, Start using One Link.
* Auto-launches via `maybeShowOnboarding()` at [`index.html:17762`](../src/one_link/web/index.html#L17762). Honors `ONBOARDING_STORAGE_KEY` in localStorage, `state.me.onboarding_completed` from the daemon, and `setup.completed` / `setup.skipped` from the One Setup API. Resumes at the right step if a previous session was interrupted.
* `_markOnboardingComplete()` persists completion to both localStorage and `/api/settings`.
* `skipOneSetup()` posts to `/api/setup` with `action: "skip"` and shows the toast "Setup is waiting in Activity whenever you want it."
* Design spec at [`docs/ONE_SETUP_FIRST_RUN_EXPERIENCE.md`](./ONE_SETUP_FIRST_RUN_EXPERIENCE.md).
* The Settings > Setup pane at [`index.html:6416-6470`](../src/one_link/web/index.html#L6416) gives the user a re-entry point + receipt list + technical-verification disclosure.
* Empty chat pane state at [`index.html:11617-11630`](../src/one_link/web/index.html#L11617) is the fallback for "wizard skipped, nothing paired yet."

**Genuinely missing:**

* No permission preflight before `getUserMedia` calls on first call. The cold browser prompt fires with no context. Failure surface today is just `"Mic access failed: ${e?.message}"` at [`index.html:18446`](../src/one_link/web/index.html#L18446).
* No first-action chips on the *post-pair empty chat* (Section 4.3.3 below). Wizard step 5 nudges the user once, but if they skip that step the chat pane is silent.
* No first-send celebration moment.
* No "What's new" modal after a daemon-version update.
* No replay-the-wizard affordance in About (other than "skipped" → next launch will reshow).

### 4.3. Concrete recommendations

#### 4.3.1. Welcome wizard

A 3-step modal that runs on first launch (gated by `state.first_run_complete` flag in localStorage + sqlite):

* **Step 1 — Identity.** Show the auto-generated display name (defaults to hostname) and let the user edit. Show the avatar color swatch (8 choices) and let them pick.
* **Step 2 — How others will find you.** Three options as radio buttons with descriptions:
  * *On the same Wi-Fi.* "Other One Link devices on your network can see you."
  * *Across networks.* "Use the rendezvous service to reach devices that aren't on your network."
  * *Strictly QR-only.* "Devices have to scan your QR to find you. Most private."
* **Step 3 — Add your first device.** Render a big QR code immediately, with text: "Open One Link on another device. Tap *Pair a new device*, then scan this." Below: a small "Skip for now" link that closes the wizard.

After this, drop the user into the main chat surface with a one-time tooltip on the sidebar pointing at the just-paired device: "This is your other device. Tap to chat with it."

#### 4.3.2. Permission preflight

Intercept the first click on 📞 voice and 📹 video. Show a small modal:

```
One Link needs your microphone [and camera] for this call.
Your browser will ask next.

Nothing is recorded or sent anywhere except to this call.
You can revoke access any time from your browser settings.

[ Continue ]   [ Not now ]
```

Only then call `getUserMedia`. This converts the cold browser prompt from "I clicked something and weird UI popped up" into "I asked for a call, the app explained, then asked permission."

#### 4.3.3. First-action prompts in empty chat

When a user pairs their first device but has zero messages, show three example actions as clickable chips below the empty state:

```
Try:
[ Drag a photo here ] [ Press 🎤 to record voice ] [ Press 📞 to call ]
```

Each chip, when clicked, runs the corresponding flow. Chip cluster auto-dismisses after the first send/call.

#### 4.3.4. First-send celebration

The first time a user sends a message to a freshly-paired device, render a brief one-time effect on the bubble: a subtle ✨ glow that fades over 1 second. This is the kind of detail iMessage uses to make moments feel rewarded.

#### 4.3.5. First-launch-after-update modal

Cheap: when daemon version changes, the next opened browser sees a small bottom-sheet: "Updated to v0.21.x. **What's new** · Bulletproof send · Click-to-open photos · Long-message collapse." With a "See full changelog" link.

#### 4.3.6. Tutorial replay

A "Show me around" button in the About pane that replays the welcome wizard for users who skipped it.

### 4.4. Onboarding edge cases

| Scenario | Current behavior | Recommended |
|---|---|---|
| First launch, no network | Empty state forever | Empty state with "Offline · waiting for network" banner |
| First launch, daemon not started | Loading spinner forever | After 5s, show "Can't reach One Link daemon. Restart the app." |
| Pair via QR fails (camera denied) | Generic error | "Camera access denied. Type the device code manually instead." |
| Pair scan succeeded but SAS doesn't match | Modal stuck | "Codes don't match. This might mean someone's intercepting. Cancel and try again." |
| Identity already exists from earlier install | Silent reuse | First-launch wizard offers "This is me again" vs. "Start fresh" |
| Migrating from another chat app | No path | "Import contacts" stub — even just an info modal explaining there's no import yet |
| Restoring from backup | Hidden in Settings | First-launch wizard step 0: "New here? Or restoring a backup?" |

## 5. Identity, pairing, discovery

### 5.1. Current state

Pairing paths shipped:

* **QR pairing.** `POST /api/v1/peer-rtc/mint-pairing` ([`server.py:1424`](../src/one_link/server.py#L1424)), `GET /api/v1/peer-rtc/qr.svg` ([`server.py:1428`](../src/one_link/server.py#L1428)). Discover modal at [`index.html:6102-6130`](../src/one_link/web/index.html#L6102). Pair modal at [`index.html:6242`](../src/one_link/web/index.html#L6242).
* **Manual key entry / ceremony.** `POST /api/peers/{fp}/pair`, `/pair-confirm`, `/pair-reject` ([`server.py:1649-1652`](../src/one_link/server.py#L1649)). SAS digits via `GET /api/peers/{fp}/sas`.
* **Group invite links.** `POST /api/groups/{gid}/invite-link` ([`server.py:1680`](../src/one_link/server.py#L1680)).
* **mDNS discovery.** `beacon.py`, `lan_discovery.py`.
* **Bluetooth proximity.** `proximity_pair_native.py`.
* **Rendezvous lookup.** `rendezvous_client.py`.

Trust states: `pending`, `pinned`, `rejected`. Verified-in-person pill at [`index.html:5654-5665`](../src/one_link/web/index.html#L5654). Key-change warning banner at [`index.html:5676-5679`](../src/one_link/web/index.html#L5676).

### 5.2. Gap analysis

#### 5.2.1. QR scanning UX

* The Discover modal shows a QR + a "scan with another device" instruction, but doesn't open the camera on the scanning side. Users have to figure out where the scanner is.
* On a device acting as the scanner, the path is "Settings > Add device > Scan QR" — three taps deep.

**Fix:** Add a prominent 🔍 *Scan* button next to the *Pair a new device* button. Tapping it requests camera permission, shows a viewfinder overlay with a QR scan-line animation, and auto-detects QR codes via the BarcodeDetector API (browser-native).

#### 5.2.2. Manual pairing

A user who can't QR (different room, accessibility, etc.) has to use SAS via the daemon API. The UI for typing a peer's pairing code manually is hidden — it's only exposed via the device drawer when a peer is already discovered. There's no "Add by code" path.

**Fix:** Add an *Enter code* input alongside the QR option. Code is a base32-encoded version of the pairing nonce, ~10 chars, human-readable in groups of 4.

#### 5.2.3. SAS verification flow

SAS digits (`GET /api/peers/{fp}/sas`) are shown during pairing. The display in the call SAS pane at [`index.html:20822`](../src/one_link/web/index.html#L20822) is good. The chat-only pairing SAS UI is less polished. Both sides should see the same words/digits and confirm Yes/No simultaneously.

**Fix:**

* Standardize on word-based SAS (5 PGP-style words, easier to verbalize than digits).
* Pairing flow always offers SAS, never skips it.
* If a user clicks "Skip verification" (anti-pattern but real), the peer is marked as `trust=blind_accepted`, NOT `trust=pinned`. The peer row shows ⚠️ until verification is completed.

#### 5.2.4. Trust visualization

Today, after pairing, every peer shows as "Verified ✓" if `trust=pinned`, regardless of HOW they got there. A blind-accepted peer looks identical to a fingerprint-verified peer.

**Fix:** Three-tier trust badge:

* 🔒🔒 *Verified in person* — both sides confirmed matching SAS.
* 🔒 *Trusted* — paired but SAS not confirmed (the default for QR pairing on the same screen, where MITM is implausible).
* ⚠️ *Unverified* — accepted without SAS, or key has changed since last verification.

Each level is clickable and opens an explainer modal.

#### 5.2.5. Key-change warning

The banner exists at [`index.html:5676-5679`](../src/one_link/web/index.html#L5676) but the copy is unknown. WhatsApp's framing is the gold standard: "Alice's security code changed. This usually means they reinstalled WhatsApp or got a new phone. You can verify by comparing safety numbers."

**Fix:** Adopt that framing. Add a "Why does this happen?" link that opens a small help modal.

#### 5.2.6. Multiple pairings to same identity

A user might pair the same physical device twice (forgot first pairing, did it again). Today this likely creates two peer rows. **Fix:** detect identical Ed25519 root key and merge / deduplicate at the UI level.

#### 5.2.7. Pairing across networks

Today the rendezvous service is opt-in via Settings > Network. New users don't know it exists. A pairing flow that fails over LAN should offer "We can't find this device on Wi-Fi. Try using the rendezvous service [Enable]?"

#### 5.2.8. NFC pairing

Modern phones support it. AirDrop uses Bluetooth + Wi-Fi-direct, comparable concept. **Fix (lower priority):** add NFC pairing as a third option for mobile-to-mobile.

### 5.3. Discovery UX

* The Discover modal lists peers, but the list-update cadence is unclear to the user. Add a small refresh indicator: "Looking for devices nearby…" with a spinner when discovery is active.
* Devices on the same identity (self-mesh) should be grouped visually under a "My devices" subheading, distinct from "Other people."
* A "Recently seen" list helps when a device was nearby an hour ago but isn't right now.

### 5.4. Invite links

Group invite links exist but per-peer (1:1) invite codes don't. **Fix:** add a "Send me a One Link invite" share sheet that generates a one-time-use pairing token, copyable as a link or QR. The recipient opens the link → One Link opens → auto-fills the pairing form.

## 17. Performance and reliability

### 17.1. Acute issues

Most are addressed in Section 3. The remaining are:

#### 17.1.1. Startup time

Goal: <2s from click to chat-visible. Measure on cold start (no cache) and warm start.

#### 17.1.2. Memory usage

Goal: <200MB for the daemon, <100MB for the browser tab. Profile and reduce.

#### 17.1.3. Battery usage on mobile

Voice / video calls are the worst offender. Ensure efficient codecs (Opus, VP9 / H.264).

#### 17.1.4. Network bandwidth on idle

Idle daemon shouldn't be transmitting unnecessarily. Audit beacon frequency, presence updates, keepalives. Aim for <5KB/min idle.

#### 17.1.5. Database growth

`state.db` grows as messages accumulate. Audit:

* Indexes on hot queries
* Vacuum on schedule (auto, not just manual button)
* Archive old messages (>90 days?) to a separate file

#### 17.1.6. Memory leaks in long-running session

A 24-hour-uptime browser tab shouldn't accumulate memory. Profile message-state, WebSocket buffers, event listeners.

#### 17.1.7. WebSocket reconnection

Verify exponential backoff. Verify that on reconnect, missed messages are caught up via a "since last seen" fetch, not just real-time from now-on.

#### 17.1.8. Service Worker outbox drain

Verify on `online` event the SW actually drains the IDB outbox AND the UI shows the messages going from "queued" to "sent".

#### 17.1.9. Transfer resume

A paused transfer should resume from where it left off, not re-send already-transferred chunks.

### 17.2. Reliability

#### 17.2.1. Crash recovery

If the daemon crashes mid-transfer, the next restart should:

* Detect the unfinished transfer
* Resume or fail-clean

#### 17.2.2. Disk full

If the user's disk is full, file receives should:

* Fail with a clear message: "Disk full. Free up space and we'll resume."
* Auto-resume when space is available

#### 17.2.3. Out-of-memory

Large file transfers shouldn't load the whole file into memory. Verify streaming.

#### 17.2.4. Clock skew

Peers with different clocks (one is 5 minutes ahead): verify timestamps render correctly (use the peer's clock not local for received messages).

#### 17.2.5. Network change mid-operation

User switches from Wi-Fi to cellular: in-flight transfers should pause and resume, calls should reconnect.

#### 17.2.6. Concurrent sessions

User opens two browser tabs to the same daemon. Verify state stays consistent (one tab's "read" propagates to the other).

#### 17.2.7. Long offline period

User offline for a week. On reconnect:

* Catch up missed messages (peers have queued them)
* Re-establish handshakes
* Surface in UI: "You missed 47 messages from Alice while offline."

## 25. Edge cases and error recovery

### 25.1. Edge case audit

| Scenario | Current behavior | Recommended |
|---|---|---|
| Disk full mid-receive | Probably fails silently | Clear toast + pause transfer until space available |
| Disk full mid-send | Same | Same: clear error, pause, retry on space |
| OOM during transfer | Probably crashes daemon | Stream everything; never load full file into memory |
| Daemon crashes mid-call | Call ends abruptly with no feedback | "Daemon restarted. Call ended." toast |
| Daemon restart while user is typing | Composer freezes | "Reconnecting…" banner, draft preserved |
| Peer's clock is wrong (5min off) | Read receipts may misbehave | Use peer's clock, not local, for inbound timestamps |
| Peer's identity changed (key rotation) | Key-change warning | Verify the warning is informative not scary |
| Peer was paired, then their device wiped | Peer shows offline forever | "Last seen 30 days ago" eventually → "Inactive" → manual archive |
| User has 100+ peers | Sidebar gets long | Pinned peers + Recent + Archived |
| User has 10,000+ messages in a chat | Scroll perf degrades | Virtualized message list (already partially done?) |
| User pastes 100,000-char text | Composer freezes | Detect, offer "Send as text file?" |
| User attaches 100 files at once | Attach tray overflows | Limit visible to 20, "+ 80 more" pill |
| User receives 100 messages in a burst | Toast spam | Coalesce: "10 new messages from Alice" single toast |
| User on cellular hits bandwidth limit | Transfers stall silently | "Bandwidth limit reached. Will resume on Wi-Fi." |
| User starts a call while on another call | Probably fails silently | "Already on a call with Bob. End that call first." |
| User declines a call while ringing both sides | Race condition | Daemon serializes call states |
| User accepts call but no answer (peer hung up) | Probably hangs | Timeout at 30s, "Other side ended the call" |
| User loses network mid-handshake | Hangs | Timeout, retry, fall back to relay if available |
| User's identity DB is corrupted | Daemon fails to start | Recovery path: "DB corrupted. Restore from backup?" |
| Concurrent edits to same message | Last-write-wins | Verify CRDT-style resolution |
| Concurrent reactions race | Lost updates? | Append-only model |
| Message arrives that's too large | Probably rejected silently | "Message too large. Asked them to retry as a file." |
| File extension mismatch (server saves wrong name) | Possible XSS / wrong app opens | Server canonicalizes name, surfaces in UI |
| User pairs same physical device twice | Two rows in peer list | Detect identical root key, dedupe |
| User deletes themselves from a group | Probably allowed | "Are you sure? You'll lose group history locally." |

### 25.2. Recovery patterns

For every failure, the system should:

1. Tell the user **what** went wrong (in plain English)
2. Tell them **why** (the underlying reason, not just the symptom)
3. Tell them **what to do** (concrete action)
4. Offer a **retry / undo** path

Today's queued-bubble surfacing of `result.after_failure.error` is exactly this pattern. Apply it everywhere.

### 27.2. Tone consistency

Strengths: human, action-oriented, occasionally humorous, blameless.

Weakness: occasionally vague ("Didn't work: …"). Every error should explain WHY.

Recommendation: a style guide with these rules:

* **Be specific.** Say what failed and why.
* **Be blameless.** Don't blame the user.
* **Be actionable.** Tell them what to do next.
* **Be human.** Avoid jargon. Allow occasional warmth or humor when it fits.
* **No em-dashes** in user-facing strings (per project convention — see `feedback_no_em_dashes.md`).
* **No exclamation points** for errors (sounds hysterical).
* **No "Oops" or "Sorry, ...".** Those are dated.
* **Capitalize like a sentence.** Not Title Case unless it's a heading.

### 27.3. Error pattern audit

For each error class, define the message template:

* **Network failure:** "Can't reach [thing]. We'll retry when the network is healthy."
* **Permission denied:** "[Thing] needs [permission] from your browser/OS. [How to grant]."
* **Validation:** "[Field] needs to be [constraint]. You entered [shown]."
* **Conflict:** "[Action] couldn't complete because [conflict]. [Resolution]."
* **Capacity:** "[Resource] is full. [What to clean up]."

### 27.4. Surfacing errors

Where errors should surface:

| Error class | Surface |
|---|---|

| Network down | Top-banner offline indicator |
| Daemon unreachable | Full-screen modal: "Can't reach One Link" |

| Call setup fail | Call overlay with reason + Retry / Send message instead |
| Capability denied | Per-bubble + per-peer card |

| Backup fail | Settings > Setup with reason |

### 36.5. Reconnect on network drop (calls)

**Trigger:** ICE connection state transitions to `disconnected` or `failed`.

**Behavior:**

* Display "Reconnecting…" banner in call surface
* Start 30s timer
* Continue listening for ICE state changes
* If `connected` again, banner dismisses silently
* If 30s elapses, end call with reason: "Connection lost"

**Implementation:**

```js
pc.addEventListener("connectionstatechange", () => {
  if (pc.connectionState === "disconnected" || pc.connectionState === "failed") {
    showReconnectingBanner();
    const timer = setTimeout(() => {
      endCall({ reason: "connection_lost" });
    }, 30000);
    pc.addEventListener("connectionstatechange", () => {
      if (pc.connectionState === "connected") {
        clearTimeout(timer);
        hideReconnectingBanner();
      }
    }, { once: true });
  }
});
```

### 36.6. Search operators

**Parser:**

```js
function parseSearchQuery(q) {
  const operators = { from: null, has: [], before: null, after: null, in: null };
  const text = q.replace(/(\w+):(\S+)/g, (m, op, val) => {
    if (op === "from") operators.from = val;
    if (op === "has") operators.has.push(val);
    if (op === "before") operators.before = parseDate(val);
    if (op === "after") operators.after = parseDate(val);
    if (op === "in") operators.in = val;
    return "";
  }).trim();
  return { operators, text };
}

function matchesQuery(msg, ops) {
  if (ops.from && !msg.from.includes(ops.from)) return false;
  if (ops.has.includes("photo") && msg.t !== "FILE_OFFER") return false;
  if (ops.has.includes("file") && msg.t !== "FILE_OFFER") return false;
  if (ops.before && msg.ts > ops.before) return false;
  if (ops.after && msg.ts < ops.after) return false;
  if (ops.in && msg.group_id !== ops.in) return false;
  if (ops.text && !msg.body?.toLowerCase().includes(ops.text.toLowerCase())) return false;
  return true;
}
```
