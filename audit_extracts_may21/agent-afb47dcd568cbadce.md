# Capability + Permission System Audit — Top 15

1. **CRITICAL** — `daemon.py:11428-11429` — **`_capability_allowed` returns `True` when `self.state is None`**. *What:* Before any policy lookup, a missing state DB short-circuits to allow. *Why:* During boot races, DB corruption, or test harnesses that null the state, every capability check passes. Combined with item 2, this is the v0.20.5 "default-allow-all" finding regrown. *Fix:* Return `False` on `state is None`; emit a single-shot SECURITY warning.

2. **CRITICAL** — `daemon.py:11440-11449` + `state.py:1439-1449` — **`policy is None` → allow-all; row-missing returns `None`**. *What:* `get_peer_capability_policy` returns `None` for any peer never written. After a fresh SAS pair, `_apply_default_capability_policy` (daemon.py:13599-13600) explicitly leaves policy=None when `pair_default_allow_all` is unset, and unset *defaults to true*. The on-disk + documented "deny-by-default" (`capabilities.py:167`) is fiction for the shipped UX. *Why:* The May 9 v0.20.5 audit flagged this; the comment at 13569-13573 now openly endorses it. *Fix:* Invert default: unset → strict; require explicit opt-in for legacy allow-all. Or migrate `None`-rows to `DEFAULT_ALLOW_AFTER_PAIRING` once.

3. **CRITICAL** — `daemon.py:11439-11448` — **Fail-open on verifier exception**. *What:* Any exception from `get_peer_capability_policy` returns `True` and bumps a counter. *Why:* Adversary-induced SQLite lock contention, disk-full, or a malformed row (item 10) flips a peer to allow-all silently. Counter is rate-not-cap. *Fix:* Fail-closed; degrade to "chat only" or full deny with explicit operator alarm.

4. **CRITICAL** — `daemon.py:4444-4448` — **CAPABILITY_GRANT accepts grants from any channel-authenticated peer regardless of pair/trust state**. *What:* `_cap_store.accept` is called with `expected_granter_pub=channel.peer_ed_pub` — no check that the granter is `pinned` or has the cap they're delegating. *Why:* A stranger/rejected peer who establishes a channel (relay, share-link redeem flow) can mint grants the local `_capability_allowed` will honor (line 11418 chain walk). Combined with the L13 delegation walker (max_depth=2) this can chain through any paired peer. *Fix:* Reject CAPABILITY_GRANT unless `state.get_peer(fp).trust == "pinned"` AND granter holds the cap themselves.

5. **CRITICAL** — `daemon.py:11418-11425` + `cap_store.py:167` — **Delegation chain walker uses NO trust filter on intermediate hops**. *What:* `_cap_authorized_via_chain` walks any stored grant. An intermediate is accepted on cycle/identity checks only, not on whether that intermediate is itself paired-and-not-rejected. *Why:* A peer revoked AFTER issuing a sub-grant remains a valid hop until the grant TTL expires (`revoke_subject`/`revoke_granter` only fires on local `revoke_peer`, not on remote revocations the granter never sent us). *Fix:* In `walk()`, drop intermediates whose `peer_record.trust != "pinned"`.

6. **HIGH** — `daemon.py:4411-4466` — **No rate limit on inbound CAPABILITY_GRANT**. *What:* Only the base64-length check (12 KB). A peer can spam thousands of grants per second; each goes through Ed25519 verify (~30 µs) plus 100k seen-nonces OrderedDict insertion. *Why:* CPU DoS + memory pressure; the OrderedDict eviction (cap_store.py:107-114) drops 10% on overflow, so a sustained flood evicts honest peers' nonces enabling replay later. *Fix:* Per-peer token bucket (e.g., 5/min) before `_cap_store.accept`; reject excess with ACK.

7. **HIGH** — `caps_grants.py:140-188` + `cap_store.py:85` — **`encode_grant` has no caveat parser; "scope" is opaque bytes**. *What:* `resource_scope` is just `bytes`. `has_capability` does exact-equality on `g.scope == query_scope`. *Why:* Folder root_id binding is enforced ONLY because callers pass the exact same bytes; no schema, no canonical form. A caller that passes UTF-8 vs raw bytes, or `folder=name` vs `folder=root_id_hex`, silently misses. There's no caveat-chain (file size, ip pin, time-of-day) — only the global `not_before/not_after`. *Fix:* Adopt the macaroon caveat list (already shipped in `cap_migration.py` per ADR-0021) as the only path; deprecate the Ed25519 raw-grant.

8. **HIGH** — `daemon.py:13565-13608` + `server.py:9667` — **`_ensure_folder_caps_for` no-ops when policy is None ("legacy allow-all")**. *What:* Comment at 9667 says "policy=None means default-allow legacy — nothing to add". *Why:* For default-allow-all peers (the common case, item 2), sharing a folder doesn't actually *narrow* their access — they already had FOLDER_SYNC. If the user later flips strict mode, the explicit folder-share consent is lost (no row exists). *Fix:* Always materialize the policy row on first share; never depend on the `None` sentinel.

9. **HIGH** — `daemon.py:8892` — **`_handle_blob_request` "no folder context" path gates on FILES only, not on the blob's origin folder**. *What:* When `folder_name` is omitted, any peer with FILES cap can pull *any* blob we hold by hash. *Why:* Two peers in different shared folders learn each other's blob hashes (via dedupe-site advertisement, gossip, or a malicious peer enumerating common blob hashes), then pull blobs they were never granted folder access to. *Fix:* Track per-blob origin folder; require the requester share that folder OR explicit "share-link redeem".

10. **HIGH** — `state.py:1447-1449` — **Malformed `allowed_json` row returns `[]` (deny-all) — silently flips an allow-policy to deny on corruption**. *What:* `json.loads` failure → `return []`. *Why:* Asymmetric with item 2: row-missing = allow-all, row-corrupt = deny-all. A partial DB write or schema drift can either lock out a paired peer entirely OR (with item 3's fail-open) flip them to allow-all on the read path. *Fix:* Raise; force operator to repair. Never silently substitute.

11. **HIGH** — `cap_root_key.py` — **No rotation API; compromise = permanent**. *What:* `load_or_create_cap_root_key` mints once; no `rotate_cap_root_key()`, no UI surface, no automatic rotation on suspected compromise. *Why:* If the cap_root key is leaked (DPAPI bypass, memory dump), every future macaroon issued under it is forgeable. The mnemonic-restore path *does* mint a fresh key, but only on a full identity-restore flow — there's no in-place rotation. *Fix:* Add `rotate_cap_root_key()` that mints a new key, writes the old one to a `cap_root.old.key` for in-flight verification, and invalidates after a grace window.

12. **MEDIUM** — `daemon.py:13610-13632` — **`_emit_capability_request` uses `time.monotonic()` dedup but no per-peer ceiling**. *What:* `CAPABILITY_REQUEST_DEDUP_S` gate is per `(fp, cap)`. A peer cycling 28 caps (LOCAL_CAPABILITIES) bypasses the dedup. *Why:* UI prompt-flood / annoyance DoS. *Fix:* Add a per-peer global ceiling (e.g., max 5 prompts per minute).

13. **MEDIUM** — `daemon.py:4444-4448` + `caps_grants.py:298-304` — **Replay defense relies on a shared, evictable seen-nonces set**. *What:* OrderedDict capped at 100k. Audit M11 fixed eviction-randomness, but not the underlying truth: an attacker who can fill the set (item 6) evicts honest nonces, then replays a captured-and-revoked grant. *Why:* The grant was already past `not_after`? Yes; expiry check (line 286-290) catches that. But a grant that's still within `not_after` and was issued + then revoked locally via `revoke_subject` — that revoke does NOT add to the replay set, so re-acceptance of the same blob re-installs the grant. *Fix:* On `revoke_*`, persist the nonces to a tombstone table; consult on `accept`.

14. **MEDIUM** — `state.py:128-148` + `caps_grants.py` grant lifecycle — **`_cap_store` is in-memory only; no durable persistence; no durable audit row for grants**. *What:* The `capability_audit` SQLite table records *policy* changes (cap_policy_set/clear/trust_set) but NOT signed-grant `accept` / `revoke_subject` / `revoke_granter` events. *Why:* On daemon restart all grants vanish (no `_cap_store.persist()`), so a revoked-then-restarted daemon loses the revocation log. Item 12 in scope ("Audit log — every capability grant/revoke gets a durable audit row?") — answer: **no**. *Fix:* Persist `_cap_store` to a SQLite table at accept/revoke time; record every accept/revoke in `capability_audit` with `kind=grant_accept|grant_revoke`.

15. **MEDIUM** — `daemon.py:4434` — **CAPABILITY_GRANT length check (12000 bytes) is post-channel-decrypt only**. *What:* The cap runs *after* base64 decode would be triggered. No earlier ceiling on the JSON envelope's `grant_b64` field at the channel-receive layer. *Why:* On a high-speed WebRTC channel a flood of 12-KB CAPABILITY_GRANTs costs ~360 MB/min of decrypt+parse before the rate limiter (which doesn't exist — item 6) fires. *Fix:* Drop the field-size cap to ~3 KB (max realistic grant ~6 caps × short scope) and add the rate limiter from item 6.
