# Crypto/Handshake Audit Findings

**1. CRITICAL — Ratchet DH-pubkey identity collision is silent replay** `double_ratchet.py:543-544, 567-573`
`decrypted_seen` tracks `(header.dh, header.n)`. After a DH ratchet the `recv_n` counter resets to 0, so a (`peer_new_dh`, n=0) tuple is recorded — but Bob's *own* `dh_send_pub` post-rotation can become `header.dh` from his *peer's view* on the next chain in 2-party churn. More importantly, the cap is `MAX_SKIP_KEYS*4 = 4000` insertions and on a long session entries get FIFO-evicted while skipped keys at `_evict_skipped_if_full` (cap 1000) live in `state.skipped`. An attacker can replay frame N once entry (dh,N) has been evicted from `decrypted_seen`; `_try_skipped` will only fail because it pops; but for already-decrypted-via-chain frames, eviction means a replay slips through the `seen_key in state.decrypted_seen` check.
**Fix:** Make `decrypted_seen` cap >= `MAX_SKIP_KEYS*N` where N covers max in-flight chains, *and* never evict an entry whose `(dh,n)` could still be replayed in the current window. Better: derive a low-water-mark per `dh` and reject anything below it.

**2. CRITICAL — `_is_small_order_x25519` returns `True` for valid pubkeys that match** `double_ratchet.py:200-205`
The function is named "is small order" but returns `matched == 1`. `matched` is OR'd from `int(compare_digest(...))` (0/1). If by adversarial accident a peer's legitimate pubkey collides with a blocklist entry it's rejected — fine. But if *two* blocklist entries had matched (impossible in current list, but the invariant is `matched in {0,1}`) the check would return `False` (since `2 != 1`) — accepting a small-order point. Even today, `matched |= 1` makes `matched == 1` whether one or many match; safe by accident.
**Fix:** Use `return matched != 0`.

**3. HIGH — recv() race-tolerance fallback silently accepts legacy ciphertext after DR is active** `channel.py:485-534`
Once `_dr_state` is set, recv() tries DR then on a broad list of errors falls back to legacy AEAD using `rx_seq` — which has NOT been advanced for any DR frame already received. An attacker who replays *any* legacy frame from before activation (or splices one) gets it accepted as long as it decrypts under the still-live legacy `rx_aead` at the current `rx_seq`. The race window is supposed to be one frame; nothing enforces "one." Worse, legacy nonces are deterministic from `rx_seq`, so an attacker who replays the legacy-AEAD frame at the exact `rx_seq` position succeeds.
**Fix:** Bound legacy fallback to exactly N=1 frame post-activation, then drop `rx_aead`/`tx_aead` and Zeroize their key material. Track `_legacy_frames_accepted_post_dr` and hard-fail past 1.

**4. HIGH — v1 HELLO signature fallback still accepted unconditionally** `channel.py:763-785`
The audit comment names this: UKS via v1-sig splice between paired peers. Counter is logged but acceptance is unconditional. The `uks_v2_only` CAPS flag hasn't shipped.
**Fix:** Add env-gated `ONE_LINK_REJECT_V1_HELLO=1` for ops to flip immediately; ship the CAPS flag.

**5. HIGH — `derive_native_transfer_secret` falls back silently when bootstrap is missing** `channel.py:220-234` + `daemon.send_file` (per memory note)
If `maybe_activate_ratchet` raised between caching `_native_transfer_seed` (line 390-396) and wiping `_dr_shared` (line 400), the seed is set — good. But if `maybe_activate_ratchet` is never called (peer doesn't advertise DR but does advertise NATIVE_TRANSFER_CAP), `_dr_shared` is still alive and used. However, on the *recv* side, `_dr_shared` is set in `respond()` and never wiped unless ratchet activates — meaning native transfer works without DR, but a peer who later activates DR without going through `maybe_activate_ratchet` (e.g. failure path at line 403-410 returns False without caching) leaves the seed underived AND `_dr_shared` still present — silent.
**Fix:** Cache `_native_transfer_seed` at the end of `initiate()`/`respond()` unconditionally; never depend on activation ordering.

**6. HIGH — Skipped-key eviction defeats OOO delivery, not the attack it's meant to stop** `double_ratchet.py:344-353`
`_evict_skipped_if_full` drops the *oldest* (FIFO). An attacker who sends a header with `header.pn = MAX_SKIP_KEYS` forces 1000 skipped-key derivations on the prior chain (line 411-419), evicting every legitimate OOO key. Receiver is then unable to decrypt any genuine delayed message that was in the cache. DoS against availability.
**Fix:** Cap `pn` advancement to `MAX_SKIP_KEYS` total *across the lifetime of a chain*, not per call. Reject headers whose `pn - state.recv_n` would overshoot remaining budget.

**7. HIGH — `_dh_ratchet` mutates state before AEAD verifies** `double_ratchet.py:549-557, 399-440`
`decrypt()` calls `_dh_ratchet` (rotates own DH keypair, advances root_key, generates new send/recv chains) BEFORE the AEAD decrypt at line 566. If AEAD fails (forged frame with a valid-looking new `header.dh`), `state.root_key`, `dh_send`, `dh_send_pub`, `prev_send_n` are already mutated. Next legitimate send uses a corrupted state; receiver can't decrypt; channel dead. Trivial DoS by any network attacker sending one bogus frame with random `header.dh`.
**Fix:** Speculatively compute the new state in locals, only commit on AEAD success. Or snapshot+rollback on InvalidTag.

**8. HIGH — `_aead_nonce` collision risk under DH-ratchet reuse** `double_ratchet.py:449-454`
Nonce is `b"\x00"*4 + struct.pack(">Q", message_number)`. The message_key is derived per-message via `kdf_chain` so (key,nonce) is unique — under correct operation. But on the receiver, `_try_skipped` pops a key and uses `_aead_nonce(header.n)`. If two skipped entries map to the same `n` across different `dh_pub` (the dict key includes dh_pub so the two entries coexist), they have different keys — safe. However, on the *send* side, after a DH-ratchet step, `send_n` resets to 0; the new send chain emits messages with nonce n=0,1,... — re-using the same nonce bytes the prior chain used. Different keys → safe by ChaCha20-Poly1305 design — *but* if `init_alice` is ever called twice on the same channel (e.g. activation retry after the broad-except at line 403), the root step uses the same `dh_priv` → same `dh_out` → same chain keys → same (key,nonce). Catastrophic.
**Fix:** Make `init_alice`/`maybe_activate_ratchet` strictly one-shot with an explicit `_dr_initialized` guard; refuse retry.

**9. MEDIUM — `verify()` swallows everything and returns False** `identity.py:455-460`
`except Exception` catches `InvalidSignature` (correct) but also `BadFormat`, `IndexError`, anything from a malformed `from_public_bytes`. A short pubkey path returns False the same as a forgery, which is OK security-wise but leaks no diagnostic — and in `channel.respond` line 761/763 the two-attempt sig check means a non-signature-related failure in the v2 attempt silently falls through to try v1. If `me.public_bytes` length is ever wrong (a packing bug elsewhere), every handshake silently downgrades to v1.
**Fix:** Catch only `InvalidSignature` (and maybe `ValueError` on pubkey length); let other exceptions raise.

**10. MEDIUM — No Zeroize anywhere; private key material lingers** `channel.py:399-401`, `identity.py:67-71`, `double_ratchet.py` throughout
`_dr_x_priv = None`, `_dr_shared = None` only drop references — Python doesn't zero the buffer. `to_pkcs8_pem` serializes the Ed25519 private to a PEM string and returns it across FFI; the string is GC'd whenever, the underlying bytes linger. RatchetState's `root_key`, chain keys, skipped MKs, `decrypted_seen` are all plain `bytes` (immutable, no zeroization). On core dump / swap / suspend image, attacker recovers post-activation keys → defeats post-compromise security claim.
**Fix:** Use `ctypes` to overwrite buffers, or move sensitive material into a `bytearray` wrapper with explicit zero-on-clear. Document the gap if not.

**11. MEDIUM — HKDF salt/info reuse between native-transfer and DR root** `channel.py:227-232` vs `355-361`
Native-transfer seed: `salt=transcript_hash, info=b"OL1/native-transfer/seed|v1"`. DR root: `salt=transcript_hash, info=DR_ROOT_INFO`. Both derive from `self._dr_shared`. Different info tags is the right design — but the *salt* is the same `transcript_hash`. HKDF-Extract with the same IKM and salt produces the same PRK; only Expand differs by info. If one downstream key leaks AND the PRK is recoverable from one expansion (it isn't, in theory, but defense-in-depth), both domains are linked.
**Fix:** Use distinct salts. e.g. `salt = transcript_hash + b"|native"` vs `+ b"|dr-root"`.

**12. MEDIUM — `note_caps_received` accepts `None` for features but `_peer_dr_capable` defaults False** `channel.py:303-313`
If the daemon ever passes `features=None` (a bug elsewhere), `feature_set` is empty, `_peer_dr_capable=False`, `_caps_received=True`. The activation will never fire, the channel will run legacy AEAD forever, and there is no loud signal. This is exactly the silent-degradation pattern.
**Fix:** Raise on `None`, or at least `log.warning` when caps payload was empty AND `DR_CAP not in features`.

**13. MEDIUM — Identity key passphrase migration path can race with concurrent daemon** `identity.py:367-413`
`load_or_create` reads `data`, tries decrypt-with-pw, falls back to decrypt-without, and if `pw` is set re-saves encrypted via `_zero_overwrite_file` + `_save_key`. Two daemons (e.g. user double-launches) both read the cleartext PEM, both decide to migrate; one runs `_zero_overwrite_file` while the other is mid-load. The second daemon's `serialization.load_pem_private_key` may already hold the parsed key (so it survives), but the on-disk file is now random/zero bytes mid-rename. If a crash hits between zero-overwrite and `os.replace`, the key file is irrecoverable garbage even with the right passphrase.
**Fix:** File lock (`fcntl`/`msvcrt.locking`) around the migration block. Also: do the atomic write FIRST, then zero-overwrite the *old* file by inode (you can't, on most FSes — so accept best-effort and document).

**14. LOW — `MAX_MSG_PER_CHAIN = 1<<32` allows nonce collision with the 64-bit nonce field** `double_ratchet.py:64, 454`
Nonce uses `>Q` (64-bit) of message_number masked to 64-bit. `MAX_MSG_PER_CHAIN = 2^32` is well below collision territory, but `_aead_nonce` does `message_number & ((1<<64)-1)` which suggests someone considered 64-bit. The cap should be much tighter than 2^32 anyway (Signal uses 2^16-ish before forcing a DH step) to limit cryptanalytic exposure on a single chain.
**Fix:** Lower `MAX_MSG_PER_CHAIN` to `1 << 20` or similar; force ratchets earlier.

**15. LOW — Handshake replay nonce window non-existent** `channel.py:686, 750`
`nonce_i` / `nonce_r` are 16 random bytes, mixed into the signed transcript. There's no peer-side cache of recently-seen `nonce_i` values — same `(i_ed, nonce_i)` arriving twice is accepted twice as separate handshakes. Not exploitable (a fresh `x_priv` makes the resulting session keys different), but it does mean an attacker can force the responder to do unbounded Ed25519+X25519 work by replaying the same valid HELLO. Cheap CPU-DoS.
**Fix:** LRU cache of recent `(peer_ed, nonce_i)` seen in last 60s; reject duplicates with a short delay.
